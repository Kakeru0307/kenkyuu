# 奏法付与層の改善案

最終更新: 2026-10-19  
実装場所: `prttype/guitar_tech/`  
関連: [`進捗スライド_ギター奏法付与.md`](../その他/スライド用/進捗スライド_ギター奏法付与.md)、[`リードフレーズデータ候補.md`](../データ/リードフレーズデータ候補.md)、[`バッキング.md`](バッキング.md) ViTex 節

実装は含まない（方針のみ）。

---

## 0. 前提

- 付与は演奏生成の**あと**（曲を作り直さない）
- 現状: 合成ルール教師の MLP（約 4500 組）。non-none 精度は低い（スライド約 15%）
- Goal-6「学習を通じて改善」は未着手
- **hyperscore の実装は当面不要**（音・FAD・奏法を動かさない）。ViTex からは思想だけ借りる

---

## 1. ViTex から借りる／借りない

| 借りる（取り組む価値あり） | 効く先 | やらない |
|---|---|---|
| **後段・注釈正本**（MIDI 書き換えを第一成果にしない） | 出力契約 → JSON 正本、render は任意 | D3PM 再生成 |
| **レイヤ分離**（演奏 / 表現 / 強弱を混ぜない） | lead 改善と奏法改善を独立に測る | hyperscore を U-Net 条件にする |
| **小節テクスチャの考え方だけ**（同時発音数・密度） | 奏法分類の入力特徴を厚くする設計 | フル hyperscore パイプライン |
| **和声は意図した進行を信頼** | 生成時メタを文脈に | 重い chord_extractor 必須化 |

hyperscore 本体（melodic/harmonic の `.npy` 出荷）は、論文でテクスチャ符号を見せる必要が出るまで後回し。

---

## 2. 現状ギャップ

- 教師が `assign_techs` のルール乱択 → 人間らしさの上限が低い
- 特徴はノート 8 次元のみ（小節密度・コード文脈なし）
- params（深さ等）は学習せず推論時ランダム
- 学習は合成モノラル carrier、推論は U-Net 多声＋ top_voice → 分布ずれ
- 成果が「書き換え MIDI」寄りで、最終形の注釈サイドカーと未整合
- val がノート単位だと carrier リークしうる
- Frame AE（`guitar_tech_last.pt`）は apply 経路外

---

## 3. 改善レバー（優先度）

| 優先 | 案 | ねらい |
|---|---|---|
| **P0** | **リードフレーズを先に良くする**（SynthTab + GuitarSet + 合成の混合。[本決め](../データ/リードフレーズデータ候補.md)） | フレーズが弱いと奏法を付けても効かない |
| **P1（設計のみ可）** | **注釈ファースト契約**: JSON 正本、render は任意 | ViTex 後段と同じ「符号が本体」 |
| **後回し** | **種類分類の強化**（TECHS・acc_nonzero） | **一旦やらなくてよい**（2026-10-19） |
| **後回し** | **params ヘッド** / 特徴拡充 / 分布寄せ / role | 分類より後でよい |

いま優先するのは **P0（リードフレーズ）**。奏法の分類精度は一旦棚上げ。

---

## 4. 成功の見方（実装時）

- 客観: val `acc_nonzero`（none 以外）
- 主観: Chu Q1–O1（付与前後の A/B。オンオフで層を切り分ける）
- 「うるささ」: multiply 系・高速フレーズでの破綻が減ること

---

## 5. やらないこと

- ViTex D3PM で MIDI を作り直すことを奏法改善と呼ぶ
- hyperscore 実装を奏法 Goal の前提にする
- 進行・キー・BPM の明示指定 CLI を本線に戻す
- 旧 lead pair / 旧 apply 教師にこだわって再学習を先延ばしする
